# ADR 003: Generic Story Concept

**Status:** Accepted

**Date:** 2025-11-24

## Context

Component documentation and presentation needs vary by target platform:
- **Storybook** for web components (React, Vue, Drupal SDC)
- **Custom documentation** for other platforms
- **Interactive demos** for design systems
- **Pattern libraries** for CMS components

We need a generic concept that:
1. Works across different platforms
2. Isn't tied to a specific tool (Storybook)
3. Can be configured per target
4. Supports various presentation formats

## Decision

We introduce the concept of a **"story"** as a generic component presentation, not tied to Storybook specifically.

### Definition

A **story** is:
- A presentation/demonstration of a component
- Shows different states and variations
- Provides interactive examples (where applicable)
- Documents usage and props
- Format determined by target conventions

### Implementation

1. **Tool naming**: `generate_story` (not `generate_storybook`)
2. **Configuration**: Story format defined in `rules/targets/{platform}/story.yaml`
3. **Format flexibility**: Can generate Storybook stories, MDX docs, HTML demos, etc.
4. **Convention-based**: Target conventions determine story structure

### For Drupal (Initial Implementation)

Story format: **Storybook with storybook-addon-sdc**

```yaml
# rules/targets/drupal/story.yaml
format: storybook
addon: storybook-addon-sdc
file_suffix: .stories.js
path: /stories
```

Generates Storybook stories that use `storybook-addon-sdc` to integrate Drupal Single Directory Components.

### For Future Targets

- **Vue**: Storybook with Vue addon
- **React**: Storybook with React addon  
- **WordPress**: Custom PHP-based pattern library
- **Laravel**: Blade-based component docs

## Consequences

### Positive

- **Platform flexibility**: Not tied to Storybook
- **Future-proof**: Easy to add new presentation formats
- **Consistent naming**: "Story" makes sense across platforms
- **Convention-based**: Each platform defines its own story format
- **Clear semantics**: "Story" = component presentation/demo

### Negative

- **Abstraction overhead**: Extra layer of abstraction
- **Naming confusion**: Might confuse developers familiar with Storybook
- **Documentation needed**: Must explain what "story" means

### Trade-offs

We accept the abstraction in exchange for:
- Platform independence
- Easier extension to non-Storybook targets
- Consistent API across all platforms

## Story Structure

Stories include:

1. **Default variant**: Base component state
2. **State variants**: Hover, active, disabled, focus
3. **Content variants**: With different content/props
4. **Responsive variants**: Mobile, tablet, desktop
5. **Theme variants**: Light/dark mode (if applicable)
6. **Interactive controls**: For testing different props

Target conventions determine which variants are generated.

## Story vs. Component

| Aspect | Component | Story |
|--------|-----------|-------|
| Purpose | Implementation | Presentation |
| Output | Code (Twig, Vue, React) | Demo/docs |
| Location | `/components` | `/stories` |
| Generated by | `generate_component` | `generate_story` |
| Format | Platform-specific | Convention-based |

## Storybook Integration (Drupal)

For Drupal with `storybook-addon-sdc`:

```javascript
// button.stories.js
import { Story } from 'storybook-addon-sdc';

export default {
  title: 'Components/Button',
  component: Story,
  argTypes: {
    variant: {
      control: 'select',
      options: ['primary', 'secondary', 'danger'],
    },
  },
};

export const Default = {
  args: {
    component: 'button',
    variant: 'primary',
    label: 'Click me',
  },
};
```

The addon loads the actual SDC component (component.yml + template.twig).

## Alternatives Considered

### Alternative 1: Hardcode Storybook

Name the tool `generate_storybook` and always generate Storybook stories.

**Rejected because:**
- Ties us to Storybook
- Not all platforms use Storybook
- Harder to add alternative presentation formats

### Alternative 2: No Abstraction

Have different tools per platform: `generate_storybook`, `generate_pattern_library`, etc.

**Rejected because:**
- Inconsistent API
- More complex for AI workflows
- Duplicates similar logic

### Alternative 3: Generate Documentation

Call it `generate_docs` instead of `generate_story`.

**Rejected because:**
- "Docs" implies text documentation, not interactive demos
- "Story" better captures the demonstration aspect
- Storybook terminology (Story) is widely understood
